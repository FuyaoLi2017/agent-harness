# V0.2 workflow runtime and replay

The runtime accepts a model-response callable and a workflow session. The session supplies a system prompt, tool schemas, and a function that returns an explicit success or error outcome for each tool call. The loop maintains the conversation, preserves model block order, and sends results from each tool batch back in one message. It owns the per-prompt eight-request budget.

The CLI creates a fresh session of the selected workflow from registered JSON metadata and Python handlers. Order management is the included workflow. Its fixture, validation, and business rules live in the order workflow. Bump the workflow version when changes to its prompt, tool behavior, or initial fixture would affect replay.

## Recording and replay

The [V0.1 trace format](v0.1.md#run-trace) is still schema version 1 and adds the following fields.

| Event | Added fields |
| --- | --- |
| `run_started` | `workflow` with an `id` and integer `version`, plus `mode` of `live` or `replay`. Interactive prompts also have a `session_id` and one-based `session_turn`. Replayed prompts have a `source_run_id`. |
| `llm_response` | Resolved `model` alongside the unchanged SDK content and usage. |
| `run_finished` | `usage` with response count, uncached input, cache creation, cache read, output, and total tokens. `cost` includes `estimated_usd` and `pricing_as_of`. |

Standalone traces sit directly under `runs/`. Interactive traces sit under `runs/<session_id>/`. A normal exit or EOF writes a `session.json` manifest with `schema_version`, `session_id`, and `prompt_count`. Replay accepts the entire directory, checks that all prompts are present, and restarts from the first prompt. V0.1 standalone traces fall back to `orders` version 1 and use the requested model when the resolved model is absent. V0.1 interactive traces cannot reconstruct their original sessions.

Replay uses recorded model responses and starts the recorded workflow version with fresh local state. It matches tool calls, tool results, and terminal outcomes in order. The recorded reply is only printed after verification. A recorded provider failure is reproduced from its sanitized reason. As in live sessions, a failed prompt leaves prior tool effects in place and keeps conversation history at the last successful prompt.

| Replay status | Meaning |
| --- | --- |
| `0` | All prompts matched, including any recorded failures. |
| `1` | A prompt diverged during replay or replay output could not be written. |
| `2` | The recording or argument combination is invalid, or the workflow version is unavailable. |

## Usage and cost

Each recorded response contributes its token counts, including responses that precede a run failure. Input includes uncached tokens and both cache categories. Output includes thinking tokens where reported. Estimates use the dated standard Claude API pricing table, including cache rates and Haiku 5.5’s per-request prompt size tiers. An unknown model, unsupported pricing mode, or missing billing details yields `null` while known token counts remain available. Replay estimates the cost of the recorded model responses.
