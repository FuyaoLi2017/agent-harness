# v0.1 — Run one synthetic order-support task

One command sends a synthetic customer request to Claude, runs local order tools as needed, prints the final answer, and leaves a JSONL trace. This is the first milestone in the [architecture and roadmap](architecture.md).

## Files and CLI

Use a flat layout. `loop.py` owns the CLI, the synchronous Messages API loop, and JSONL logging. `tools.py` owns the static tool schemas and handlers. `orders.json` is the fixture. Use `argparse`, `json`, and the standard library for local work. The Anthropic SDK handles the model request.

```sh
uv run --locked python loop.py "Please refund the mug from order ORD-1001."
```

The CLI accepts one nonempty synthetic task and an optional `--model` override. The task text is sent to Claude and recorded verbatim in the local trace. The default model is `claude-opus-5-5`. Read the API key from `ANTHROPIC_API_KEY`. Report a missing key or invalid arguments on stderr and exit 2 before starting a run. Print the trace path to stderr. After logging a successful finish, print the final answer to stdout and exit 0. Exit 1 for an unsuccessful run.

## Model and tool loop

1. Load a fresh copy of the fixture, open the run log, and start the message history with the task. Use a fixed system prompt that describes the store rules, tells Claude to consult tools for order facts, and requires a successful tool result before claiming a cancellation or refund.
2. Request a synchronous Anthropic Messages response with the full static tool list, `max_tokens=1024`, and SDK retries disabled. Count each model request toward the eight-request limit. Log every response before handling its stop reason.
3. On `tool_use`, check that another model request remains before dispatching any calls. Append the assistant's complete content in block order, dispatch the calls in that order, and append all matching results as one immediately following user message. Use the original tool-call ID in each `tool_use_id`. Encode each tool result as JSON text and set `is_error: true` for expected errors. Keep earlier messages, the system prompt, and the tool list stable through the run. [Claude tool-call handling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
4. On `end_turn`, join the text blocks with newlines and finish. Use the following terminal outcomes for the remaining cases. [Claude stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

| Outcome | Status | Behavior |
| --- | --- | --- |
| Final answer | `ok` | Print a nonempty answer and exit 0. |
| `refusal` | `refused` | Report the refusal on stderr and exit 1. |
| `max_tokens` | `truncated` | Keep the response in the trace and exit 1. |
| Request eight returns `tool_use` | `budget_exceeded` | Stop before dispatching that response's tools and exit 1. |
| API error, unexpected stop, or invalid response | `failed` | Record a short reason code, report the error on stderr, and exit 1. An empty final answer is an invalid response. |

## Synthetic order tools

Load the fixture relative to `loop.py`. Its top-level `customer_id` and ISO date `as_of` supply the trusted identity and clock for the whole run. Each record in `orders` has `order_id`, `customer_id`, `status` (`pending`, `shipped`, `delivered`, or `cancelled`), `delivered_on` (ISO date or null), an opaque `payment_ref`, `items`, and `refunded_item_ids`. Each item has `item_id`, `name`, and `price_cents` in USD. Hold changes in memory until the process exits.

The three tools are an explicit allowlist. Use JSON object schemas with the listed required fields and validate arguments again before dispatch. Each ID is a nonempty string. Use the same `order_not_found` error for an unknown order and an order owned by a different customer.

| Tool | Arguments | Result and rules |
| --- | --- | --- |
| `get_order` | `order_id` | Return the status, delivery date, item details, and refunded item IDs for an owned order. Keep the payment reference internal. |
| `cancel_order` | `order_id` | Change `pending` to `cancelled` and return the current status. A repeat cancellation returns the same status. Shipped and delivered orders return an error. |
| `issue_refund` | `order_id`, `item_ids` | Require a delivered order with a delivery date 0–30 calendar days before `as_of`, inclusive. Require a nonempty list of distinct, known, unrefunded item IDs. Sum item prices and return `approval_required` above 50,000 cents. On success, mark all selected items refunded in memory and return their IDs, the amount in cents, and confirmation of a simulated refund to the original payment method. |

Complete all checks before changing an order. Unknown tools, invalid arguments, ownership errors, and policy denials return a JSON error with a short code and explanation. The loop reports these as tool results so Claude can recover. Tool handlers only read and update the local synthetic fixture state.

## Run trace

Create `runs/<run_id>.jsonl` with a new UUID for each started run and flush each appended line. The common envelope is `schema_version` set to 1, a contiguous `seq` starting at 1, a UTC `ts`, and `type`. Open the trace before requesting Claude. If writing fails, report the error and stop the run. Store only synthetic demo inputs and sanitized error data.

| Event | Payload |
| --- | --- |
| `run_started` | `run_id`, `task`, `model`. |
| `llm_response` | `turn` starting at 1, `stop_reason`, complete serialized `content` blocks in their original order, and SDK `usage` fields. |
| `tool_intent` | `turn`, `call_id`, `name`, `args`. Append before dispatch. |
| `tool_result` | `turn`, `call_id`, `is_error`, and `content` as sent back to Claude. |
| `run_finished` | `status`, `output` for success, or a short `reason` for other outcomes. |

The trace supports inspection and provides data for later replay and cost accounting. Crash recovery and durable refund reconciliation arrive in v0.4.

## Acceptance checks

- Use a fixture with an owned `ORD-1001`, a mug priced at 25 USD, and a delivery date ten days before `as_of`. Run the example with a configured API key. Expect a simulated refund of 2,500 cents, a final answer, and a parseable JSONL trace with a matching refund intent and successful result before `run_finished`.
- Check that a pending order can be cancelled twice with the same resulting status. Check that a second refund for the same item in one run, an out-of-window order, an order owned by another customer, and a refund above 500 USD all produce tool errors and leave fixture state unchanged.
- Exercise malformed arguments and multi-call responses. Expect one result per call ID in a single user message. Check that a refusal, truncation, provider failure, and last-turn tool request all produce the specified exit status and trace outcome. The last-turn request dispatches no tools.
- Start a second run and confirm it sees the original fixture values. Inspect the generated trace and confirm its sequence is contiguous and it contains no API key.
